# 다음 한칸 v0.1 — 데이터 모델 초안

## 결론

v0.1에서는 `정체성 / 목표 / 프로젝트 / 작업 / 다음 한칸`을 5개 테이블로 나누지 않고, 하나의 계층형 테이블 `structure_items`에 통합한다.

이유:

- 다섯 단계가 공통적으로 제목, 설명, 상태, 순서, 상위/하위 연결을 가진다.
- `parent_id` 하나로 정방향/역방향 탐색을 모두 만들 수 있다.
- 구조 화면의 펼치기/접기와 항목 이동이 단순해진다.
- 단계가 바뀌어도 공통 CRUD를 재사용할 수 있다.
- 과거 `onekan_state`처럼 앱 전체 상태를 JSON 한 덩어리로 저장하지 않아 충돌 위험을 줄인다.

## 1. structure_items

핵심 테이블.

권장 필드:

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | uuid | PK |
| `user_id` | uuid | 소유 사용자 |
| `type` | text/enum | `identity`, `goal`, `project`, `task`, `next_step` |
| `title` | text | 제목 |
| `description` | text nullable | 설명 |
| `parent_id` | uuid nullable | 같은 테이블의 상위 항목 |
| `status` | text/enum | `active`, `completed`, `archived`, `stopped` |
| `sort_order` | integer | 같은 부모 안에서의 순서 |
| `start_date` | date nullable | 필요할 때만 사용 |
| `due_date` | date nullable | 목표/프로젝트/작업 등에 선택적으로 사용 |
| `completed_at` | timestamptz nullable | 완료 시각 |
| `archived_at` | timestamptz nullable | 보관 시각 |
| `created_at` | timestamptz | 생성 시각 |
| `updated_at` | timestamptz | 수정 시각 |

### parent_id 규칙

v0.1에서는 한 항목은 상위 항목을 최대 1개만 가진다.

권장 계층:

- `identity` → 부모 없음
- `goal` → `identity` 또는 부모 없음
- `project` → `goal` 또는 부모 없음
- `task` → `project` 또는 부모 없음
- `next_step` → `task` 또는 부모 없음

독립된 작업/다음 한칸을 허용하므로 `parent_id`는 nullable이다.

여러 목표에 같은 프로젝트를 연결하는 다중 부모 구조는 v0.1 범위에서 제외한다. 필요해지면 추후 별도 relation 테이블을 추가한다.

## 2. user_focus

홈의 `지금 한칸`을 어떤 항목으로 보여줄지 저장한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `user_id` | uuid | PK, 사용자 |
| `current_item_id` | uuid nullable | 현재 집중할 `next_step` |
| `updated_at` | timestamptz | 변경 시각 |

`structure_items`에 `is_focus=true` 같은 플래그를 여러 행에 두는 것보다 사용자당 한 행으로 관리하는 편이 안전하다.

## 3. UI 상태

다음 값은 v0.1에서 Supabase에 저장하지 않고 브라우저 `localStorage`로 관리한다.

- 구조 보기 방향: `forward` / `reverse`
- 펼쳐진 항목 ID 목록
- 마지막으로 선택한 구조 항목
- 마지막 구조 필터

이 값들은 데이터 자체가 아니라 UI 편의 상태이므로, 초기 버전에서는 DB 복잡도를 늘리지 않는다.

추후 여러 기기에서 동일한 화면 상태를 유지할 필요가 생기면 `user_view_preferences` 테이블을 추가한다.

## 4. 정방향 / 역방향 탐색

### 정방향

`parent_id = 현재 항목 id`인 행을 찾아 자식으로 내려간다.

`정체성 → 목표 → 프로젝트 → 작업 → 다음 한칸`

### 역방향

현재 행의 `parent_id`를 따라 올라간다.

`다음 한칸 → 작업 → 프로젝트 → 목표 → 정체성`

한 테이블을 쓰기 때문에 양방향 탐색에 별도 연결 테이블이 필요하지 않다.

## 5. 쪼개기 저장 방식

`작업(task)`을 쪼갤 때 생성되는 실행 단계는 v0.1에서 `next_step`으로 저장한다.

예:

```text
작업: 메인 페이지 디자인
  ├─ 다음 한칸: 레퍼런스 3개 찾기
  ├─ 다음 한칸: 와이어프레임 그리기
  └─ 다음 한칸: 컬러 정하기
```

그중 지금 실행할 하나를 `user_focus.current_item_id`로 지정한다.

즉 `다음 한칸`은 하나만 존재하는 것이 아니라 여러 개 존재할 수 있고, 그중 하나가 `지금 한칸`이 될 수 있다.

## 6. 완료 처리

기본 규칙:

- `next_step` 완료 → 해당 항목만 완료
- `task`의 모든 `next_step`이 완료되어도 상위 `task`를 자동 완료하지 않는다.
- 대신 `모든 다음 한칸이 완료되었습니다. 작업도 완료할까요?`처럼 사용자가 결정하게 한다.
- `project`, `goal`도 같은 방식으로 자동 완료보다는 명시적 완료를 우선한다.

이유: 실제 프로젝트에서는 하위 항목을 모두 끝낸 뒤 추가 작업이 생길 수 있으므로 자동 완료가 과도할 수 있다.

## 7. 진행률

v0.1에서는 DB에 `progress_percent`를 직접 저장하지 않는 것을 우선한다.

화면에서 필요하면 하위 항목 상태로 계산한다.

예:

- 프로젝트: 완료 작업 수 / 전체 작업 수
- 목표: 완료 프로젝트 수 / 전체 프로젝트 수
- 작업: 완료 다음 한칸 수 / 전체 다음 한칸 수

정체성은 퍼센트 진행률보다 연결된 활성 목표 수를 보여주는 방식이 더 자연스럽다.

사용자가 직접 진행률을 입력하는 기능은 추후 검토한다.

## 8. 삭제 / 보관

기본 동작은 삭제보다 보관을 우선한다.

- `completed`: 끝낸 항목
- `archived`: 더 이상 현재 구조에서는 쓰지 않지만 보관
- `stopped`: 중단한 항목

상위 항목을 삭제한다고 하위 항목까지 DB에서 연쇄 삭제하지 않는다.

가능하면 FK의 `ON DELETE SET NULL` 방향을 우선 검토한다. 실제 hard delete는 별도 확인 과정을 둔다.

## 9. 정렬

각 항목은 `sort_order`를 가진다.

정렬 기준:

1. 같은 `parent_id`
2. `sort_order`
3. 필요 시 `created_at`

드래그로 순서를 바꿀 때 해당 형제 항목들의 `sort_order`만 변경한다.

## 10. 보안 / RLS 원칙

`structure_items`와 사용자별 테이블은 반드시 `user_id` 기준으로 사용자 자신의 행만 읽고 쓸 수 있게 한다.

기본 원칙:

- SELECT: `auth.uid() = user_id`
- INSERT: 생성되는 `user_id`가 `auth.uid()`와 같아야 함
- UPDATE: 기존 행과 수정 후 행 모두 사용자 소유인지 확인
- DELETE: 사용자 소유 행만 가능

실제 Supabase 스키마 생성 단계에서 최신 Supabase 권장 방식과 보안 advisor를 다시 확인한다.

## 11. v0.1에서 만들지 않는 테이블

아직 만들지 않는다.

- 태그
- 협업/공유
- 댓글
- 알림
- 반복 규칙
- 캘린더 연결
- 시간추적
- AI 쪼개기 기록
- 다중 부모 관계
- 상세 변경 이력

1. 데이터 모델 최종 검토
2. Supabase에 새 테이블 생성
3. RLS 설정 및 검증
4. 데모 데이터 대신 `structure_items` 읽기

6. 쪼개기 → `next_step` 생성 연결
