# 다음 한칸 v0.1 — 데이터 모델

## 구현 상태

**2026-09-12 Supabase 실제 스키마 구현 완료.**

대상 프로젝트: 기존 오늘한칸과 같은 Supabase 프로젝트. 기존 `onekan_state` 및 과거 테이블은 삭제/변경하지 않고 그대로 보존했다.

구현된 핵심:

- `public.structure_items`
- `public.user_focus`
- RLS 활성화
- `authenticated` 역할에 필요한 CRUD 권한 명시 부여
- 사용자 소유 행만 접근 가능한 SELECT/INSERT/UPDATE/DELETE 정책
- 부모/자식 단계 검증 트리거
- `user_focus`는 활성 상태의 `next_step`만 가리킬 수 있도록 검증
- 집중 중인 `next_step`이 완료/보관/중단되면 `user_focus.current_item_id` 자동 해제
- `updated_at` 자동 갱신
- 조회/FK용 인덱스 구성
- 다른 사용자 `user_id`로 쓰기 시도 차단 테스트 통과
- 정체성 → 목표 → 프로젝트 → 작업 → 다음 한칸 전체 연결 테스트 통과

Supabase Advisor 기준으로 새 테이블에 대한 RLS 누락이나 FK 인덱스 누락 경고는 해소했다. 현재 남아 있는 Advisor 경고는 기존 오늘한칸 레거시 테이블 또는 프로젝트 공통 Auth 설정에 대한 항목이다.

---

## 결론

v0.1에서는 `정체성 / 목표 / 프로젝트 / 작업 / 다음 한칸`을 5개 테이블로 나누지 않고, 하나의 계층형 테이블 `structure_items`에 통합한다.

이유:

- 다섯 단계가 공통적으로 제목, 설명, 상태, 순서, 상위/하위 연결을 가진다.
- `parent_id` 하나로 정방향/역방향 탐색을 모두 만들 수 있다.
- 구조 화면의 펼치기/접기와 항목 이동이 단순해진다.
- 단계가 바뀌어도 공통 CRUD를 재사용할 수 있다.
- 과거 `onekan_state`처럼 앱 전체 상태를 JSON 한 덩어리로 저장하지 않아 충돌 위험을 줄인다.

## 1. structure_items

핵심 테이블.

| 필드 | 실제 타입/기본값 | 설명 |
|---|---|---|
| `id` | `uuid`, `gen_random_uuid()` | PK |
| `user_id` | `uuid` | 소유 사용자, `auth.users` 참조 |
| `type` | `text` | `identity`, `goal`, `project`, `task`, `next_step` |
| `title` | `text` | 제목, 공백 제외 1~200자 |
| `description` | `text nullable` | 설명 |
| `parent_id` | `uuid nullable` | 같은 테이블의 상위 항목 |
| `status` | `text`, 기본 `active` | `active`, `completed`, `archived`, `stopped` |
| `sort_order` | `integer`, 기본 `0` | 같은 부모 안에서의 순서 |
| `start_date` | `date nullable` | 선택적 시작일 |
| `due_date` | `date nullable` | 선택적 기한 |
| `completed_at` | `timestamptz nullable` | 완료 시각 |
| `archived_at` | `timestamptz nullable` | 보관 시각 |
| `created_at` | `timestamptz`, 기본 `now()` | 생성 시각 |
| `updated_at` | `timestamptz`, 기본 `now()` | 수정 시각, 트리거로 자동 갱신 |

### parent_id 규칙

v0.1에서는 한 항목은 상위 항목을 최대 1개만 가진다.

- `identity` → 부모 없음
- `goal` → `identity` 또는 부모 없음
- `project` → `goal` 또는 부모 없음
- `task` → `project` 또는 부모 없음
- `next_step` → `task` 또는 부모 없음

독립된 `goal`, `project`, `task`, `next_step`도 허용한다.

DB 트리거가 다음을 강제한다.

- 자기 자신을 부모로 지정할 수 없음
- 다른 사용자의 항목을 부모로 지정할 수 없음
- 잘못된 단계 연결 금지
- 생성 후 `type` 변경 금지

여러 목표에 같은 프로젝트를 연결하는 다중 부모 구조는 v0.1 범위에서 제외한다. 필요해지면 추후 relation 테이블을 추가한다.

## 2. user_focus

홈의 `지금 한칸`을 저장한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `user_id` | `uuid` | PK, 사용자 |
| `current_item_id` | `uuid nullable` | 현재 집중할 `next_step` |
| `updated_at` | `timestamptz` | 변경 시각, 자동 갱신 |

규칙:

- 사용자당 최대 1행
- 자기 소유 항목만 지정 가능
- `type = next_step`만 지정 가능
- `status = active`인 항목만 지정 가능
- 집중 중인 `next_step`이 `completed`, `archived`, `stopped`로 바뀌면 자동으로 집중 해제
- 항목이 hard delete되면 FK `ON DELETE SET NULL`

`structure_items`에 `is_focus=true` 같은 플래그를 여러 행에 두는 방식보다 사용자당 한 행으로 관리하는 편이 안전하다.

## 3. UI 상태

다음 값은 v0.1에서 Supabase에 저장하지 않고 브라우저 `localStorage`로 관리한다.

- 구조 보기 방향: `forward` / `reverse`
- 펼쳐진 항목 ID 목록
- 마지막으로 선택한 구조 항목
- 마지막 구조 필터

이 값들은 데이터 자체가 아니라 UI 편의 상태이므로 초기 버전에서는 DB 복잡도를 늘리지 않는다.

추후 여러 기기에서 동일한 화면 상태를 유지할 필요가 생기면 `user_view_preferences` 테이블을 추가한다.

## 4. 정방향 / 역방향 탐색

### 정방향

`parent_id = 현재 항목 id`인 행을 찾아 자식으로 내려간다.

`정체성 → 목표 → 프로젝트 → 작업 → 다음 한칸`

### 역방향

현재 행의 `parent_id`를 따라 올라간다.

`다음 한칸 → 작업 → 프로젝트 → 목표 → 정체성`

한 테이블을 쓰기 때문에 양방향 탐색에 별도 연결 테이블이 필요하지 않다.

## 5. 쪼개기 저장 방식

`작업(task)`을 쪼갤 때 생성되는 실행 단계는 v0.1에서 `next_step`으로 저장한다.

```text
작업: 메인 페이지 디자인
  ├─ 다음 한칸: 레퍼런스 3개 찾기
  ├─ 다음 한칸: 와이어프레임 그리기
  └─ 다음 한칸: 컬러 정하기
```

그중 지금 실행할 하나를 `user_focus.current_item_id`로 지정한다.

즉 `다음 한칸`은 여러 개 존재할 수 있고 그중 하나가 `지금 한칸`이 된다.

## 6. 완료 처리

기본 규칙:

- `next_step` 완료 → 해당 항목만 완료
- 해당 항목이 `지금 한칸`이면 DB에서 집중 상태 자동 해제
- `task`의 모든 `next_step`이 완료되어도 상위 `task`는 자동 완료하지 않음
- 대신 `모든 다음 한칸이 완료되었습니다. 작업도 완료할까요?`처럼 사용자가 결정
- `project`, `goal`도 같은 방식으로 명시적 완료를 우선

실제 프로젝트에서는 하위 항목을 모두 끝낸 뒤 추가 작업이 생길 수 있으므로 자동 완료가 과도할 수 있다.

## 7. 진행률

v0.1에서는 DB에 `progress_percent`를 직접 저장하지 않는다.

화면에서 하위 항목 상태로 계산한다.

- 프로젝트: 완료 작업 수 / 전체 작업 수
- 목표: 완료 프로젝트 수 / 전체 프로젝트 수
- 작업: 완료 다음 한칸 수 / 전체 다음 한칸 수

정체성은 퍼센트보다 연결된 활성 목표 수를 보여주는 방식이 더 자연스럽다.

## 8. 삭제 / 보관

기본 동작은 삭제보다 보관을 우선한다.

- `completed`: 끝낸 항목
- `archived`: 현재 구조에서는 쓰지 않지만 보관
- `stopped`: 중단한 항목

상위 항목을 hard delete해도 하위 항목은 연쇄 삭제하지 않고 `parent_id`가 `NULL`이 된다.

사용자 계정 자체가 삭제될 경우 해당 사용자의 신규 구조 데이터는 `auth.users` FK에 따라 함께 정리된다.

## 9. 정렬 / 인덱스

정렬 기준:

1. 같은 `parent_id`
2. `sort_order`
3. 필요 시 `created_at`

현재 인덱스:

- `structure_items_user_id_idx`
- `structure_items_parent_id_idx`
- `structure_items_user_parent_sort_idx`
- `structure_items_user_type_status_idx`
- `user_focus_current_item_idx`

새 테이블 직후에는 Advisor가 인덱스를 `unused`로 표시할 수 있는데, 실제 데이터/트래픽이 아직 없는 초기 상태이므로 정상이다.

## 10. 보안 / RLS

두 테이블 모두 RLS 활성화.

`anon`에는 테이블 권한을 부여하지 않는다.

`authenticated`에는 다음 권한만 명시적으로 부여한다.

- SELECT
- INSERT
- UPDATE
- DELETE

각 동작은 사용자 자신의 `user_id`에 대해서만 허용한다.

RLS 정책에서는 최신 Supabase 권장 성능 패턴인 `(select auth.uid()) = user_id`를 사용한다.

UPDATE는 기존 행 소유권 확인을 위한 `USING`과 수정 후 소유권 확인을 위한 `WITH CHECK`를 모두 둔다.

### 검증 결과

실제 인증 역할을 가정한 DB 트랜잭션 테스트에서 다음을 확인했다.

1. 다른 사용자 `user_id`로 INSERT → RLS 차단
2. 정체성 생성 성공
3. 목표 → 정체성 연결 성공
4. 프로젝트 → 목표 연결 성공
5. 작업 → 프로젝트 연결 성공
6. 다음 한칸 → 작업 연결 성공
7. `user_focus`에 활성 `next_step` 지정 성공
8. 해당 `next_step`을 완료 처리 → `user_focus` 자동 해제 성공
9. 테스트 데이터는 트랜잭션 rollback으로 실제 DB에 남기지 않음
